# Chat Runtime 长任务活性与进展超时设计

## 背景

Chat Runtime 当前把一次用户任务的模型请求、上下文压缩和工具续轮统一限制在 300 秒内。工具执行还存在固定时长超时：AI SDK 工具策略为 60 秒，Renderer 工具链同时受到 30 秒请求等待边界约束。

固定总时长可以阻止失控任务永久占用资源，但也会终止仍在正常推进的 Agent 长任务。单纯删除这些超时同样不安全：现有 `loading` 或 `executing` 只能说明工具尚未返回，不能区分有效执行、无响应、循环心跳、等待外部条件或执行器失联。

本设计以端到端活性与进展协议替代 Chat Runtime 的固定任务总时长，让持续推进的长任务继续运行，同时保留无响应检测、取消传播、兼容工具边界和用户可见状态。

## 目标

- 取消 Chat Runtime 单次用户任务的 300 秒固定总时限。
- 将工具的固定执行时长限制改为基于活性、实质进展和等待状态的分层策略。
- 让 Main、Renderer 与支持进度通知的 MCP 工具使用同一套状态语义。
- 保留模型流停滞、工具执行器失联、重复工具调用和用户主动停止等安全边界。
- 让工具长时间运行、无实质进展、等待用户、等待外部条件和执行中断具有不同的可见状态与错误代码。
- 保持不支持进度协议的旧工具可继续运行，并明确其兼容超时行为。

## 非目标

- 本轮不实现任意普通工具在应用重启后的透明断点续跑。
- 本轮不把超时参数开放到设置页。
- 本轮不移除非 Chat Runtime 的自动命名、结构化摘要等一次性 AI 调用的总时限。
- 本轮不依赖 UI `loading`、动画或轮询渲染状态判断工具是否仍有进展。
- 本轮不为不支持进度通知的第三方 MCP 工具伪造进度。

## 核心原则

### 活性不等于进展

- `heartbeat` 仅证明执行器仍可通信。
- `progress` 必须携带可验证的新状态，例如阶段变化、完成数量增加、新输出片段或产物更新。
- 静态 `loading`、重复心跳和相同进度快照不能更新最后实质进展时间。

### 长任务不使用固定墙钟上限

Chat Runtime 任务只要模型流、工具和续轮仍满足各自的活性边界，就可以持续运行。任务级安全边界由以下机制共同承担：

- 模型流停滞超时。
- 工具活性超时。
- 连续重复工具调用收口。
- 用户手动停止。
- Runtime 结束后的晚到事件隔离。

### 超时所有权唯一

主进程 Chat Runtime 中的工具执行 Watchdog 是长任务工具超时的唯一事实来源。Renderer、Main 工具和 MCP 适配器只上报事件，不直接修改 Runtime 的截止时间，也不能通过 UI 状态自行续期。

## 分层超时策略

| 边界 | 默认策略 | 到期行为 |
| --- | --- | --- |
| Chat Runtime 用户任务 | 不设置固定总时限 | 由下层活性边界和用户停止收敛 |
| 模型流 | 连续 90 秒没有流数据 | 中止当前模型请求并归一化为流停滞错误 |
| 工具活性 | 连续 60 秒没有开始确认、心跳或实质进展 | 中止工具并返回 `TOOL_UNRESPONSIVE` |
| 工具进展提醒 | 连续 60 秒只有心跳、没有实质进展 | 保持执行，投影“仍在运行”并提示继续等待或停止 |
| 等待用户 | 暂停活性与进展时钟 | 用户提交、拒绝或取消后恢复或结束 |
| 等待外部条件 | 必须包含 `retryAt` 和 `deadlineAt` | 到 `retryAt` 允许重试；到 `deadlineAt` 返回 `EXTERNAL_WAIT_TIMEOUT` |
| 旧工具兼容执行 | 使用工具当前静态超时；未指定时默认 60 秒 | 返回兼容超时错误，适配进度协议后切换 Watchdog |
| 非 Chat Runtime AI 调用 | 保留 300 秒总时限及现有局部超时 | 维持现有一次性调用失败语义 |

工具进展提醒不会停止执行，也不会把“继续等待”伪造成新进展。“继续等待”只确认用户已看到提醒，并从当前时刻重新计算下一次提醒窗口。

支持活动协议的执行器默认每 15 秒发送一次心跳；任意一次被接受的 `started`、`heartbeat` 或 `progress` 都会更新活性时间，因此连续丢失四个默认心跳周期才会触发 60 秒活性超时。

## 工具状态模型

每个 `toolCallId` 独立维护以下状态：

| 状态 | 含义 | 允许的后继状态 |
| --- | --- | --- |
| `starting` | Runtime 已接收调用，执行器尚未确认开始 | `executing`、`waiting_user`、`failed`、`cancelled` |
| `executing` | 执行器存活，且未达到进展提醒阈值 | `running_idle`、`waiting_user`、`waiting_external`、终态 |
| `running_idle` | 执行器存活，但连续 60 秒没有实质进展 | `executing`、`waiting_user`、`waiting_external`、终态 |
| `waiting_user` | 等待用户确认、输入或选择 | `executing`、`failed`、`cancelled` |
| `waiting_external` | 等待网络、限流或其他外部条件 | `executing`、`failed`、`cancelled` |
| `stopping` | 已发送取消信号，等待执行器释放资源 | `cancelled`、`failed` |
| `completed` | 工具成功完成 | 无 |
| `failed` | 工具失败或执行器无响应 | 无 |
| `cancelled` | 用户或 Runtime 取消工具 | 无 |
| `interrupted` | Runtime 恢复时发现原执行链已经丢失 | 无 |

`loading` 继续作为消息和界面的展示字段，但不属于 Watchdog 状态机，也不参与任何计时判断。

## 活动事件协议

工具执行链路向 Watchdog 上报统一活动事件。每个事件包含：

- `runtimeId`：所属 Runtime。
- `toolCallId`：所属工具调用。
- `sequence`：由单个执行器单调递增的序号。
- `occurredAt`：执行器观察到事件的时间。
- `kind`：`started`、`heartbeat`、`progress`、`waiting` 或 `resumed`。`completed` 与 `failed` 继续使用现有结构化工具结果协议，避免活动事件和结果事件竞争终态。

`progress` 事件额外包含受约束的进展快照：

- `phase`：当前稳定阶段标识。
- `completed` 与可选 `total`：可度量工作量。
- `message`：面向用户的短说明。
- 可选产物引用：只传递稳定标识和安全元数据，不内联大型内容。

`waiting` 事件必须区分用户等待和外部等待。外部等待必须带 `retryAt` 与 `deadlineAt`；缺少期限的外部等待事件按无效事件拒绝，工具继续受活性时钟约束。

Watchdog 只接受当前活跃 Runtime、当前工具调用和大于已接收序号的事件。终态之后的事件、旧 Runtime 事件和乱序事件直接丢弃。

所有超时判断都使用主进程接收事件时读取的单调时钟。`occurredAt` 只用于诊断和界面展示，不能直接修改截止时间，避免 Renderer 时钟偏移或伪造时间戳绕过超时。

## Watchdog 组件

主进程新增独立的工具执行 Watchdog，职责包括：

- 为每个工具调用维护当前状态、最后心跳时间、最后实质进展时间、等待信息和提醒确认时间。
- 校验活动事件的身份、顺序、状态转换和进展是否真实变化。
- 管理活性计时器、进展提醒计时器和外部等待截止时间。
- 在活性超时或外部等待超时时触发统一中止控制器。
- 向 Runtime 投影状态变化与节流后的进展快照。
- 在 Runtime 结束时释放计时器，并拒绝后续事件续期。

工具不能获得 Watchdog 或截止时间的直接引用。执行上下文只暴露受限的活动上报器，避免工具任意暂停、重置或延长计时器。

## 各执行边界接入

### Main 工具

Main 工具执行输入通过不可枚举属性获得活动上报器，与现有不可枚举 `AbortSignal` 保持一致，避免活动控制对象进入日志、持久化快照或重复工具调用比较。

现有可暂停工具超时控制器迁移为 Watchdog 的等待状态事件。文件搜索、子进程和其他长工具在产生新输出、阶段变化或工作量变化时上报 `progress`，空闲计算期间按默认 15 秒间隔上报 `heartbeat`。

### Renderer 工具

Renderer 工具协议增加活动事件 IPC。Renderer 收到工具请求后先发送 `started`，执行期间发送心跳和进展，最终仍通过现有结果提交协议收敛。

现有 Renderer 请求的 30 秒边界拆分为传输/开始确认边界：30 秒内未确认 `started` 视为 Renderer 不可达；确认开始后由 Watchdog 的 60 秒活性边界管理，不再用同一个定时器限制整个执行时长。

普通组件的 `loading` 状态不能调用活动 IPC。只有实际持有 `runtimeId + toolCallId` 执行上下文的工具执行器可以上报。

### MCP 工具

MCP 适配器始终请求服务端进度通知，并在收到通知时把它映射为统一活动事件。映射前执行频率、长度和身份校验。

MCP 协议没有可依赖的工具级“支持进度通知”发现标志，因此调用先进入旧工具兼容观察期：首个有效进度通知在 60 秒内到达时，适配器清除兼容静态计时器并把调用升级到 Watchdog；60 秒内没有进度通知时仍按旧静态超时返回 `TOOL_TIMEOUT`。升级后不得同时保留兼容静态计时器和 Watchdog 计时器。不根据连接仍存在、客户端 Spinner 或重复轮询推断进展。本轮不提供用户设置入口。

### AI SDK 与非 Runtime 调用

Chat Runtime 的 AI SDK 请求只保留模型流停滞边界，不再通过 `totalMs` 或 SDK `toolMs` 间接获得新的任务总时限；Runtime 执行的工具统一交给 Watchdog。

非 Chat Runtime 的直接 AI 调用继续使用现有固定总时限和 SDK 工具超时，避免自动命名、摘要或后台辅助调用永久占用资源。实现时应拆分常量命名，避免继续用一个 `AI_REQUEST_TIMEOUT` 同时表达长任务和一次性调用语义。

## 数据投影与持久化

- `heartbeat` 只更新内存活性时间，不写数据库、不产生用户消息。
- `progress` 在通过实质变化校验后更新内存快照，并按每个工具调用最多每秒一次的频率合并持久化，避免高频写入。
- `waiting_user`、`waiting_external`、`running_idle` 和终态立即投影，确保重新打开会话时能解释任务停留原因。
- 消息 Part 只保存最后一份安全进展快照和状态，不保存完整事件历史。
- Runtime 恢复时，非终态且没有可恢复执行契约的工具收敛为 `interrupted`，不会仅凭持久化心跳或 `loading` 重建执行器。
- 已具备独立 checkpoint 的工具可以在后续设计中通过新调用从检查点重启；本轮不直接复活旧 Promise 或进程。

## 用户交互

工具卡片按状态展示：

- `执行中`：展示最新阶段或进度。
- `仍在运行`：执行器有心跳，但 60 秒没有实质进展；展示最后进展距今时间。
- `等待用户`：展示需要的确认、输入或选择。
- `等待外部条件`：展示原因和预计重试时间。
- `无响应`：执行器活性超时，工具已中止。
- `正在停止`：取消信号已发送，正在释放资源。
- `已中断`：应用退出、进程丢失或 Runtime 恢复时无法恢复执行链。

`running_idle` 提供“继续等待”和“停止”操作。继续等待只推迟下一次提醒；停止走统一取消链路。用户不需要在每次心跳或进度变化时处理通知。

## 取消与资源释放

用户停止、Runtime 关闭、活性超时和外部等待超时都通过同一根中止控制器传播到：

- Main 工具。
- Renderer 工具执行器。
- 子进程与文件搜索。
- 支持取消的 MCP 请求。

取消后先进入 `stopping`。执行器应在 5 秒宽限期内自行释放资源；受控子进程在宽限期结束后仍未退出时执行强制终止。强制终止只针对当前工具明确持有的进程标识，禁止使用宽泛进程匹配。

## 错误语义

新增或细分以下稳定错误代码：

- `TOOL_UNRESPONSIVE`：执行器在活性窗口内没有心跳或进展。
- `EXTERNAL_WAIT_TIMEOUT`：工具声明的外部等待截止时间已到。
- `USER_CANCELLED`：用户主动停止或拒绝继续。
- `RUNTIME_INTERRUPTED`：恢复时无法重建原执行链。

`running_idle` 是可见运行状态，不是错误。兼容工具的旧静态超时在迁移完成前可以继续返回 `TOOL_TIMEOUT`。错误结果应作为结构化工具结果返回模型，使模型可以解释、重试或选择替代路径，不能全部折叠为 `REQUEST_FAILED`。

## 安全与流量约束

- 活动事件的 `message` 最多包含 500 个 Unicode 字符，产物只允许安全引用。
- 每个工具调用最多每秒接受一次心跳；更高频的心跳直接丢弃。进度事件可以在内存中合并，但每个通过实质变化校验的最新快照仍更新活性与进展时间，持久化频率最多每秒一次。
- 相同进度快照不更新最后实质进展时间。
- 事件日志只记录工具名、状态、错误代码和时间统计，不记录工具输入、完整输出或敏感内容。
- Runtime 结束后先关闭 Watchdog，再释放工具注册，避免竞态事件复活任务。

## 兼容与迁移顺序

1. 引入活动事件类型、Watchdog 与纯状态机测试，不改变现有超时行为。
2. 接入 Main 工具并迁移现有暂停/恢复控制。
3. 接入 Renderer 开始确认、心跳、进展和取消事件。
4. 接入支持进度通知的 MCP 工具；其余工具保留兼容静态超时。
5. 将 Chat Runtime 模型流和工具超时所有权切换到新策略。
6. 删除 Chat Runtime 任务级 300 秒时钟与硬编码提示。
7. 保留并重新命名非 Chat Runtime 一次性 AI 调用的 300 秒边界。
8. 最后启用 `running_idle` 用户交互和持久化投影。

先建立并验证 Watchdog，再删除任务总时限，避免迁移期间出现没有任何兜底的执行窗口。

## 测试策略

### 状态机与计时

- `progress` 同时更新最后活性与最后实质进展时间。
- `heartbeat` 只更新最后活性时间。
- 相同进度快照不能规避进展提醒。
- 静态 `loading` 不影响任何计时器。
- 等待用户期间暂停活性与进展时钟，恢复后继续使用剩余时间。
- 外部等待缺少期限时被拒绝，有效期限到期后返回 `EXTERNAL_WAIT_TIMEOUT`。
- 活性超时后中止执行器并返回 `TOOL_UNRESPONSIVE`。
- 终态、乱序和旧 Runtime 活动事件不能续期或改变结果。

### 执行边界

- Main 工具活动上报器不进入日志、快照和模型上下文。
- Renderer 在开始确认前使用传输边界，确认后由 Watchdog 接管。
- Renderer、Main、子进程和 MCP 的中止信号完整传播。
- 支持进度通知的 MCP 工具可以续期；不支持的工具继续使用静态超时。
- 子进程在取消宽限期结束后只终止自身明确持有的进程。

### Runtime 与兼容回归

- Chat Runtime 连续运行超过 300 秒且持续满足活性边界时不会失败。
- 模型流连续 90 秒没有数据仍会失败。
- 连续重复工具调用仍进入最终回答收口。
- 非 Chat Runtime 的一次性 AI 调用仍受 300 秒总时限保护。
- Runtime 恢复把不可恢复的执行中工具标记为 `interrupted`。
- 心跳不产生数据库写放大，进展持久化遵守合并频率。

### 用户界面

- 工具卡片正确区分执行中、仍在运行、等待用户、等待外部条件、无响应、正在停止和已中断。
- “继续等待”只推迟提醒，不修改最后实质进展时间。
- “停止”只影响目标 Runtime 和目标工具调用。

## 验收标准

- 有真实活动的 Chat Runtime 任务运行超过 300 秒后仍能继续并正常完成。
- 工具持续发送有效心跳时不会因总执行时长达到 60 秒而被终止。
- 工具只有心跳、没有实质进展时进入可见的 `running_idle`，但不会自动伪装成推进中。
- 工具连续 60 秒没有任何有效活动时被可靠中止，且底层执行器收到取消信号。
- 等待用户不消耗工具活性时间，外部等待不会无限期暂停。
- Renderer、Main、MCP 和兼容工具具有明确且可测试的差异化策略。
- 删除 Chat Runtime 300 秒限制不会改变非 Runtime 一次性调用的既有保护。
